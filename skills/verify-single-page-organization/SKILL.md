# 단일 페이지 구조 정리 검증

## 목적

주석 추가 및 코드 위치 정리 작업이 코드 동작, 공개 인터페이스, 실행 순서, API 계약을 변경하지 않았는지 검증한다.

정리 결과가 지정된 기능 블록 및 레이어 분류 기준에 맞는지도 확인한다.

프로젝트에 정의된 포맷 검사와 타입 검사를 실행하고, 성공 여부와 남은 위험을 명확히 보고한다.

검증은 다음 두 축을 모두 포함한다.

1. 코드 동작과 인터페이스가 보존되었는가
2. 선언이 책임과 의존성에 따라 올바른 레이어에 분류되었는가

## 필수 입력

* 구조 정리 전후의 diff
* 수정된 단일 페이지 파일
* 구조 정리 전의 단일 페이지 파일 또는 해당 Git revision
* 프로젝트의 `AGENTS.md`
* `package.json` 또는 이에 준하는 빌드 설정
* 프로젝트에서 사용하는 포맷 및 타입 검사 설정
* 구조 정리에 사용한 레이어 정의 또는 `organize-single-page-code` 지침

## 절대 제약

* 검증 과정에서 기능을 추가하지 않는다.
* 실패한 검사를 통과시키기 위해 관련 없는 코드를 수정하지 않는다.
* 변수명, 함수명, 타입명, 컴포넌트명, hook 이름, API 또는 동작을 임의로 변경하지 않는다.
* 기존 오류를 이번 변경으로 발생한 오류처럼 보고하지 않는다.
* 실행하지 않은 검사를 성공했다고 표현하지 않는다.
* 정적 검토만 수행한 항목을 실행 검증된 것처럼 표현하지 않는다.
* 분류가 잘못되었다는 이유로 함수 본문을 리팩터링하거나 분리하지 않는다.
* 검증 단계에서 파일 구조를 다시 설계하지 않는다.
* 포맷터가 변경한 결과를 검토하지 않은 채 그대로 승인하지 않는다.
* 단순히 함수라는 이유만으로 `lib` 분류가 적절하다고 판단하지 않는다.
* 위치 이동이 존재한다는 이유만으로 동작 보존을 자동 판정하지 않는다.
* diff에서 삭제 후 추가된 코드가 동일해 보여도 초기화 시점과 상대적 실행 순서를 별도로 확인한다.

## 레이어 검증 기준

레이어는 선언의 이름이나 문법적 형태가 아니라 실제 책임과 의존성을 기준으로 검증한다.

허용되는 레이어는 다음과 같다.

```ts
/* type */
/* api */
/* hook */
/* container */
/* helper */
/* lib */
```

빈 레이어 주석은 허용하지 않는다.

### `type`

다음 선언만 포함되는지 확인한다.

* `type`
* `interface`
* 타입 전용 generic alias
* props, emit, row, request, response 등 컴파일 타임 타입 선언

다음 코드가 `type`에 포함되면 오분류 가능성을 보고한다.

* 런타임 객체
* validation schema
* 상수
* 함수
* enum처럼 사용하는 객체 리터럴

### `api`

API 요청을 직접 수행하거나 특정 API 호출을 캡슐화하는 선언인지 확인한다.

적절한 예:

```ts
const fetchItems = (params: SearchParams) =>
  $api.get("/items", { params });
```

다음이 포함되면 `container` 오분류 가능성을 확인한다.

* loading 상태 변경
* API 호출 결과를 컴포넌트 상태에 대입
* 성공 또는 오류 알림 호출
* modal 또는 router 호출
* 여러 API와 상태 변경을 순서대로 조합
* 사용자 이벤트 전체 흐름 처리

API 호출이 기존 함수 본문 내부에 직접 포함되어 있고 별도 함수로 분리되지 않았다면, 검증 단계에서 이를 분리하라고 요구하지 않는다. 함수 전체의 주된 책임이 업무 흐름이면 `container`가 적절할 수 있다.

### `hook`

React hook, Vue/Nuxt composable 또는 프레임워크 컨텍스트 획득 호출인지 확인한다.

적절한 예:

```ts
const { t } = useI18n();
const { $api } = useNuxtApp();
const route = useRoute();
```

다음을 확인한다.

* hook 호출 자체와 반환값 획득 선언만 포함되는가
* hook 결과를 사용하는 모든 일반 함수가 무분별하게 `hook`으로 분류되지 않았는가
* React hook 호출 순서가 변경되지 않았는가
* hook이 조건문, 반복문 또는 조기 반환 이후로 이동하지 않았는가
* custom hook 또는 composable 호출의 상대적 순서가 유지되었는가

### `container`

페이지 또는 기능의 상태, 파생 상태, 이벤트 처리, 업무 흐름과 부수 효과를 담당하는 선언인지 확인한다.

포함 가능 대상:

* state, `ref`, `reactive`
* `computed`, memoized state
* 상태를 읽거나 변경하는 함수
* 사용자 이벤트 핸들러
* API 호출과 상태 반영을 조합하는 함수
* modal, notification, router, storage 호출
* watcher, effect, lifecycle
* 여러 실행 단계를 조합하는 orchestration 함수
* 화면 또는 업무 기능의 주요 규칙

다음 특성을 가진 함수가 `helper` 또는 `lib`에 배치되어 있으면 오분류 가능성을 보고한다.

* 상태를 변경함
* API를 호출함
* modal, router, notification, storage를 호출함
* 실행 순서 자체가 업무 의미를 가짐
* 사용자 이벤트에 직접 연결됨
* 여러 함수를 순서대로 호출해 하나의 업무를 완료함

### `helper`

현재 페이지 또는 현재 기능 구현을 보조하는 작은 함수인지 확인한다.

포함 가능 대상:

* 번역 key prefix wrapper
* 현재 컴포넌트 상태를 읽는 단순 판별 함수
* 현재 기능 전용 데이터 접근 함수
* 요청 파라미터 또는 옵션 객체 생성 함수
* 반복 표현을 줄이는 wrapper
* 현재 페이지에 종속된 formatting 또는 mapping 함수
* hook이나 composable에서 얻은 값에 의존하는 작은 보조 함수

적절한 예:

```ts
const wr = (key: string) =>
  t(`wrcvit.${key}`);

const hasSelectedWarehouse = () =>
  selectedWarekey.value !== "";

const createSearchParams = () => ({
  compkey: compkey.value,
  warekey: selectedWarekey.value,
});
```

다음을 확인한다.

* 부수 효과를 발생시키는 함수가 `helper`에 들어가 있지 않은가
* API, modal, router, notification을 직접 호출하는 함수가 `helper`에 들어가 있지 않은가
* 현재 컴포넌트와 무관한 순수 함수가 불필요하게 `helper`로 분류되지 않았는가
* 특정 기능 전용 helper가 공통기능으로 잘못 올라가 있지 않은가

helper가 상태를 읽는 것은 허용될 수 있지만 상태를 변경하거나 외부 부수 효과를 실행하면 일반적으로 `container` 가능성을 우선 검토한다.

### `lib`

외부 상태와 현재 컴포넌트에 의존하지 않는 독립적인 순수 계산·변환·검증 로직인지 확인한다.

원칙적으로 다음 조건을 모두 만족해야 한다.

* 입력값만으로 결과를 계산함
* 동일 입력에 대해 동일 출력을 반환함
* 컴포넌트 state, ref, props, context를 직접 읽지 않음
* hook 또는 composable 결과에 의존하지 않음
* API, router, modal, notification, storage를 호출하지 않음
* 외부 상태를 변경하지 않음
* 현재 locale이나 런타임 설정에 따라 결과가 달라지지 않음
* 별도 파일로 이동해도 의미가 유지됨
* 독립적인 단위 테스트가 가능함

적절한 예:

```ts
const normalizeWarekey = (value: string) =>
  value.trim().toUpperCase();
```

다음은 `lib` 오분류로 보고한다.

```ts
const wr = (key: string) =>
  t(`wrcvit.${key}`);
```

이 함수는 번역 함수와 현재 locale에 의존하므로 `helper`에 가깝다.

```ts
const isSelectedRow = (row: RowData) =>
  row.warekey === selectedWarekey.value;
```

이 함수는 컴포넌트 상태에 의존하므로 `helper` 또는 책임에 따라 `container`에 가깝다.

```ts
const saveRows = async () =>
  $api.post("/rows", rows.value);
```

이 함수는 API 호출이라는 부수 효과가 있으므로 `api` 또는 `container`에 가깝다.

## 검증 절차

### 1. 검증 환경 및 지침 확인

코드를 검토하기 전에 다음 파일을 확인한다.

1. 저장소 루트 및 대상 파일 인접 경로의 `AGENTS.md`
2. `package.json`
3. lockfile
4. 포맷터 설정
5. linter 설정
6. TypeScript 또는 프레임워크 타입 검사 설정
7. 구조 정리에 사용한 레이어 정의

상위 디렉터리와 하위 디렉터리에 여러 `AGENTS.md`가 있다면 대상 파일에 적용되는 범위를 확인한다.

프로젝트의 package manager는 lockfile과 저장소 지침을 기준으로 결정한다.

예:

* `pnpm-lock.yaml` → pnpm
* `yarn.lock` → Yarn
* `package-lock.json` → npm

저장소 지침이 lockfile과 다르면 저장소 지침을 우선하며 충돌 사실을 보고한다.

### 2. 변경 범위 확인

먼저 버전 관리 diff와 작업 트리 상태를 확인한다.

가능한 경우 다음 명령을 사용한다.

```bash
git status --short
git diff --stat
git diff --name-status
git diff -- <target-file>
```

staged 변경도 검증 범위에 포함되는 경우 다음을 추가로 확인한다.

```bash
git diff --cached --stat
git diff --cached -- <target-file>
```

다음을 확인한다.

* 대상 파일 외의 파일이 수정되지 않았는가
* 파일 생성, 삭제, 이름 변경 또는 분리가 발생하지 않았는가
* 단일 페이지 파일이 유지되었는가
* 변경이 주석 추가와 선언 위치 이동 중심인가
* 코드 블록의 내용이 수정되지 않고 이동만 되었는가
* 문자열, 숫자, 정규식, 조건식 또는 연산자가 변경되지 않았는가
* import 및 export가 변경되지 않았는가
* 포맷 변경과 의미 변경이 구분되는가

대상 외 파일에 기존 변경이 있다면 무조건 실패로 처리하지 않는다. 다만 이번 작업에서 발생한 변경인지 기존 작업 트리에 이미 존재한 변경인지 구분할 수 없으면 잔여 위험으로 기록한다.

### 3. 정리 전후 코드 대응 확인

삭제된 코드와 추가된 코드가 위치만 이동한 것인지 확인한다.

가능하면 선언 단위로 다음을 비교한다.

* 선언 이름
* 선언 종류
* 함수 매개변수
* 함수 본문
* 반환 표현식
* type annotation
* generic parameter
* 초기값
* 객체 key와 value
* 배열 요소
* callback 본문
* 옵션 객체
* 주석을 제외한 token 구성

공백과 주석 차이를 제거했을 때 코드 내용이 동일한지 확인한다.

다음 항목은 단순 위치 이동으로 보지 않는다.

* 함수 선언문을 함수 표현식으로 변경
* `const`를 `let`으로 변경
* optional chaining 추가 또는 제거
* nullish coalescing 변경
* 조건식 순서 변경
* 객체 property 순서 변경으로 실행 의미가 달라질 가능성이 있는 경우
* destructuring 순서 또는 default value 변경
* async, await 추가 또는 제거
* callback을 별도 함수로 추출
* 반환값 생략 또는 추가
* type assertion 변경
* generic 인자 변경
* import type 전환
* 표현식 축약 또는 확장

### 4. 식별자 및 공개 인터페이스 보존 확인

diff를 기준으로 다음 항목의 변경 여부를 확인한다.

* 변수명
* 함수명
* 타입명
* interface명
* 컴포넌트명
* props 이름
* emit 또는 event 이름
* hook 및 composable 이름
* import된 식별자
* export된 식별자
* template ref 이름
* DOM id, class 또는 selector
* slot 이름
* route name
* store key
* injection key

다음 공개 인터페이스도 확인한다.

* `defineProps`
* `defineEmits`
* `defineExpose`
* React component props
* exported function 또는 type
* default export
* named export
* template에서 참조하는 식별자

주석과 위치 이동 이외의 변경이 있으면 구체적인 diff 위치와 의미를 보고한다.

### 5. API 계약 보존 확인

다음 항목을 정리 전후로 비교한다.

* API client 또는 호출 함수
* HTTP method
* endpoint
* URL 조합 방식
* path parameter
* query parameter
* request body
* header
* timeout 또는 request option
* 응답 destructuring
* 응답 매핑
* 오류 처리
* 반환값
* await 여부
* 호출 횟수
* 호출 순서

특히 객체 property가 재배치된 경우에도 getter, spread, computed property 또는 side effect가 포함될 수 있으므로 무조건 의미가 없다고 판단하지 않는다.

다음 변경은 API 계약 변경 가능성으로 보고한다.

* parameter 누락 또는 추가
* spread 순서 변경
* default 값 변경
* body와 query 위치 변경
* response field 접근 경로 변경
* 성공 또는 실패 처리 순서 변경
* API 호출을 조건문 안이나 밖으로 이동
* API 호출의 await 제거
* 병렬 실행과 순차 실행 간 변경

### 6. 실행 순서 및 초기화 순서 검토

다음 위험을 집중적으로 확인한다.

* 함수 표현식 또는 변수 선언이 사용 지점 뒤로 이동함
* `const`, `let`, class 선언이 초기화 전에 참조됨
* 모듈 초기화 시 실행되는 코드의 순서 변경
* 즉시 실행 함수의 상대적 순서 변경
* computed property 초기화 순서 변경
* watcher, effect 또는 subscription 등록 순서 변경
* lifecycle hook 등록 순서 변경
* container 생성 시점 변경
* helper 초기화 시점 변경
* closure가 참조하는 값의 초기화 시점 변경
* decorator 또는 metadata 등록 순서 변경
* 같은 이름의 shadowing 범위 변경
* block scope 변경
* 순환 참조 가능성
* temporal dead zone 발생 가능성
* getter 또는 proxy 접근 시점 변경
* default parameter 평가 시점 변경
* side effect가 있는 초기값의 평가 순서 변경

함수 선언문은 hoisting되더라도 함수 표현식, class, `const`, `let`은 동일하게 취급하지 않는다.

선언을 이동했지만 해당 선언의 초기값이 단순 함수 객체 생성이 아닌 경우, 이동으로 인해 side effect 시점이 바뀌지 않았는지 확인한다.

예:

```ts
const value = createValue();
```

`createValue()`가 호출되는 선언은 단순 선언 이동이 아니라 실행 시점 이동일 수 있다.

정적 검토만으로 확정할 수 없는 항목은 `확인됨`으로 표현하지 않고 잔여 위험으로 기록한다.

### 7. React hook 및 프레임워크 생명주기 검토

React 코드라면 다음을 확인한다.

* hook 호출 개수 유지
* hook 호출 순서 유지
* hook이 조건문 또는 반복문 안팎으로 이동하지 않음
* 조기 반환 전후로 hook이 이동하지 않음
* `useEffect`, `useLayoutEffect`, `useMemo`, `useCallback`의 상대적 순서 유지
* dependency array 변경 없음
* effect cleanup 변경 없음
* custom hook 호출 순서 유지

Vue 또는 Nuxt 코드라면 다음을 확인한다.

* `ref`, `reactive`, `computed` 초기화 순서 변화의 영향
* `watch`, `watchEffect` 등록 순서
* lifecycle hook 등록 순서
* `useRoute`, `useRouter`, `useI18n`, `useNuxtApp` 등 composable 호출 위치
* SSR 또는 setup 실행 시점에 영향을 줄 수 있는 이동
* template에서 참조하는 선언의 유효성
* top-level await의 상대적 순서

프레임워크별 규칙이 적용되지 않는 경우 해당 검사는 `해당 없음`으로 기록할 수 있다.

### 8. 기능 블록 구조 검사

다음을 확인한다.

* 공통기능 블록이 필요한 경우 적절한 위치에 존재하는가
* 공통기능 블록이 무조건 생성된 것은 아닌가
* 공통기능에는 둘 이상의 업무 기능이 실제로 사용하는 선언만 포함되는가
* 하나의 기능에서만 사용하는 선언이 공통기능에 포함되지 않았는가
* 업무 기능별 구분선이 사용되었는가
* 구분선 형식이 요청된 형식과 일치하는가
* 기능 블록 이름이 구현 세부사항이 아니라 사용자의 업무 행위를 나타내는가
* 화면 설정과 페이지 렌더링 등 페이지 조립 코드가 적절한 기능 블록에 있는가
* 하나의 선언이 관련 없는 기능 블록에 배치되지 않았는가
* 기능 간 공유 여부를 단순 참조 횟수만으로 판단하지 않았는가

공통기능 구분선은 정확히 다음 형식인지 확인한다.

```ts
/* -------------------------------------------------------------------------- */
/* 공통기능                                                                    */
/* -------------------------------------------------------------------------- */
```

기능 구분선은 다음 형식인지 확인한다.

```ts
/* -------------------------------------------------------------------------- */
/* 품목 검색 기능                                                              */
/* -------------------------------------------------------------------------- */
```

기능 블록명은 실제 파일의 업무 의미를 기준으로 판단한다. 예시에 나온 이름과 일치할 필요는 없다.

### 9. 레이어 주석 및 분류 검사

다음을 확인한다.

* 레이어 주석이 `type`, `api`, `hook`, `container`, `helper`, `lib` 중 하나인가
* 다른 임의의 레이어명이 추가되지 않았는가
* 코드가 없는 빈 레이어 주석이 없는가
* 기능 내부의 레이어 순서가 가능한 범위에서 기준 순서를 따르는가
* 실행 순서 보존을 위해 순서가 달라진 경우 그 이유가 타당한가
* 각 선언이 실제 책임에 맞는 레이어에 위치하는가

기준 레이어 순서는 다음과 같다.

1. `type`
2. `api`
3. `hook`
4. `container`
5. `helper`
6. `lib`

레이어 순서보다 실행 순서와 hook 호출 순서가 우선한다. 따라서 순서가 다르다는 이유만으로 실패 처리하지 않는다.

대신 다음을 구분해서 보고한다.

* 안전한 재배치가 가능하지만 순서가 맞지 않음
* 실행 순서 보존 때문에 의도적으로 순서가 다름
* 판단 근거 없이 혼재되어 있음

### 10. `lib` 오분류 집중 검사

모든 `lib` 선언을 개별적으로 검토한다.

각 함수에 대해 다음 질문을 적용한다.

1. 컴포넌트의 state, ref, props 또는 context를 읽는가
2. hook 또는 composable에서 얻은 값에 의존하는가
3. API, router, modal, notification, storage를 호출하는가
4. 외부 객체를 변경하는가
5. 현재 locale, 시간, 랜덤값 또는 런타임 환경에 따라 결과가 달라지는가
6. 동일 입력에 대해 동일 출력을 보장하는가
7. 별도 파일로 이동해도 독립적으로 의미가 유지되는가

1번부터 5번 중 하나라도 참이면 일반적으로 `lib` 오분류 가능성을 보고한다.

6번과 7번이 참이고 외부 의존성이 없다면 `lib` 분류를 적절한 것으로 볼 수 있다.

다음과 같은 패턴은 특히 확인한다.

```ts
const label = (key: string) => t(`prefix.${key}`);
```

번역기와 locale에 의존하므로 `helper` 가능성이 높다.

```ts
const isSelected = (row: RowData) =>
  row.id === selectedId.value;
```

컴포넌트 상태를 읽으므로 `helper` 가능성이 높다.

```ts
const openModal = () =>
  $appModal.open(...);
```

부수 효과가 있으므로 `container` 가능성이 높다.

```ts
const fetchRows = () =>
  $api.get(...);
```

API 호출을 직접 캡슐화하면 `api`, 상태 변경과 업무 흐름까지 포함하면 `container` 가능성이 높다.

### 11. `helper`와 `container` 경계 검사

모든 `helper` 선언에 대해 다음을 확인한다.

* 값을 계산하거나 판별하거나 객체를 생성하는가
* 현재 컴포넌트에 종속된 작은 보조 역할인가
* 상태를 직접 변경하지 않는가
* 외부 부수 효과를 실행하지 않는가
* 주요 이벤트 흐름이나 업무 절차를 담당하지 않는가

다음과 같은 함수는 `container` 가능성을 보고한다.

```ts
const handleSave = async () => {
  loading.value = true;
  await $api.post(...);
  loading.value = false;
};
```

```ts
const openDetail = () => {
  $appModal.open(...);
};
```

다음과 같은 함수는 `helper`가 적절할 수 있다.

```ts
const createSearchParams = () => ({
  compkey: compkey.value,
});
```

```ts
const hasSelection = () =>
  selectedId.value !== "";
```

단순 판별 함수라도 실제 사용자 이벤트를 직접 처리하거나 상태 변경을 포함하면 `container`로 검토한다.

### 12. `api`와 `container` 경계 검사

API 호출 함수가 다음 중 어디에 해당하는지 확인한다.

`api`:

* 서버 요청 자체를 캡슐화
* 요청 인자를 받아 API를 호출
* 응답을 반환
* 화면 상태를 직접 변경하지 않음
* modal, notification, router를 직접 호출하지 않음

`container`:

* loading 상태 변경
* API 호출 전후 검증
* API 응답을 화면 상태에 반영
* 성공 또는 오류 메시지 처리
* modal 또는 화면 전환 처리
* 여러 요청이나 함수를 순서대로 조합
* 사용자 이벤트에 직접 연결

기존 함수가 API 호출과 상태 변경을 함께 수행했다면 검증 단계에서 강제로 분리하지 않는다. 해당 함수 전체가 `container`에 배치되었는지만 확인한다.

### 13. 공통기능 판정 검사

공통기능 블록의 각 선언에 대해 실제 사용 위치를 확인한다.

다음을 만족하는지 검토한다.

* 둘 이상의 서로 다른 업무 기능에서 사용됨
* 페이지 전체 설정 또는 페이지 조립에 실질적으로 공유됨
* 단순히 파일 상단에 있었기 때문에 공통으로 분류되지 않음
* 동일 기능 내부 여러 함수에서 사용된다는 이유만으로 공통으로 분류되지 않음

예를 들어 검색 기능 내부의 세 함수가 같은 helper를 사용하더라도 다른 업무 기능에서는 사용하지 않는다면 해당 helper는 검색 기능 전용이다.

공통 선언이 특정 기능에만 사용된다면 오분류로 보고한다.

### 14. 검사 명령 탐색

프로젝트 설정에서 공식 명령을 우선 탐색한다.

우선순위:

1. 대상 파일에 적용되는 `AGENTS.md`에 명시된 명령
2. `package.json` scripts
3. 저장소 공식 문서
4. CI 설정
5. 사용 중인 도구의 표준 검사 명령

명령을 추측하기 전에 설정 파일을 확인한다.

다음 종류의 명령을 구분한다.

* 포맷 검사
* 포맷 적용
* lint
* 타입 검사
* 단위 테스트
* 빌드

예:

```bash
pnpm format:check
pnpm lint
pnpm typecheck
```

프로젝트가 pnpm 또는 Yarn을 사용하면 해당 package manager를 그대로 사용한다.

검사 전용 명령이 존재하는데 포맷 적용 명령을 대신 실행하지 않는다.

### 15. 포맷 검사 실행

프로젝트에 포맷 검사 전용 명령이 있으면 이를 우선 실행한다.

예:

```bash
pnpm format:check
```

포맷 적용 명령만 존재하고 사용자가 포맷 실행까지 요구한 경우에만 적용 명령을 실행한다.

예:

```bash
pnpm format
```

포맷 적용 명령을 실행하기 전후로 diff를 확인한다.

다음을 구분한다.

* 공백 변경
* 줄바꿈 변경
* 주석 정렬
* trailing comma
* quote 변경
* 표현식 또는 코드 구조 변경

포맷터가 주석이나 공백 이외의 의미 있는 코드를 변경했다면 별도로 보고한다.

포맷 적용으로 대상 외 파일이 변경되었다면 해당 파일과 변경 원인을 보고한다.

### 16. lint 검사 실행

프로젝트에 lint 명령이 정의되어 있다면 실행한다.

예:

```bash
pnpm lint
```

lint 실패를 다음과 같이 구분한다.

* 이번 위치 이동 또는 주석 변경으로 새로 발생한 오류
* 대상 파일에 이미 존재했던 오류
* 대상 외 파일의 기존 오류
* 환경 또는 dependency 문제
* 자동 수정이 필요한 오류

검증 단계에서는 사용자가 명시적으로 요청하지 않는 한 `--fix`를 임의로 실행하지 않는다.

### 17. 타입 검사 실행

프로젝트에 정의된 타입 검사 명령을 실행한다.

예:

```bash
pnpm typecheck
```

전체 프로젝트 타입 검사만 존재하면 해당 명령을 실행한다.

전체 검사가 광범위하거나 오래 걸릴 수 있다는 이유로 임의의 부분 검사 명령을 성공 판정 기준으로 대체하지 않는다.

검사를 실행할 수 없는 경우 다음을 보고한다.

* 실행하려 한 명령
* 실행할 수 없었던 이유
* 누락된 dependency 또는 환경
* 검증되지 않은 범위

타입 검사 실패는 다음과 같이 구분한다.

* 이번 정리 변경에서 발생한 오류
* 기존 오류로 판단되는 항목
* 대상 외 파일의 오류
* 환경 또는 generated type 부재로 인한 오류
* 관련성을 확정할 수 없는 오류

기존 오류 여부를 확정할 수 없다면 추측하지 않고 `관련성 미확정`으로 보고한다.

### 18. 선택적 테스트 또는 빌드 검사

`AGENTS.md`나 프로젝트 지침에서 필수로 요구하는 경우에만 테스트 또는 빌드 명령을 실행한다.

예:

```bash
pnpm test
pnpm build
```

포맷 및 타입 검사만 요청된 경우 불필요한 전체 빌드를 자동으로 성공 기준에 추가하지 않는다.

다만 실행하지 않은 테스트나 빌드는 `미실행`으로 명확히 기록한다.

### 19. 최종 diff 재검토

포맷, lint, 타입 검사 후 diff와 작업 트리를 다시 확인한다.

가능한 경우 다음 명령을 사용한다.

```bash
git status --short
git diff --stat
git diff --name-status
git diff -- <target-file>
```

다음을 최종 확인한다.

* 포맷터가 예상 밖의 코드를 변경하지 않았는가
* 대상 외 파일이 추가로 변경되지 않았는가
* 주석 정리와 안전한 위치 이동 외 의미 변경이 없는가
* 검사 과정에서 생성된 임시 파일이 남지 않았는가
* cache, report, generated file이 추적 대상 변경으로 남지 않았는가
* 최종 파일의 레이어 분류가 최초 검토 결과와 달라지지 않았는가

### 20. 최종 판정 기준

#### `확인됨`

다음을 모두 만족할 때 사용한다.

* diff에서 의미 변경을 발견하지 못함
* 식별자와 공개 인터페이스가 보존됨
* API 계약 변경을 발견하지 못함
* 실행 순서와 hook 순서의 위험을 발견하지 못함
* 기능 블록과 레이어 분류가 기준에 부합함
* 필수 포맷 및 타입 검사가 성공함
* 실행 환경으로 인해 검증하지 못한 핵심 범위가 없음

#### `주의 필요`

다음 중 하나라도 해당하면 사용한다.

* 정적 검토만으로 실행 순서 안전성을 확정하기 어려움
* 일부 필수 검사를 환경 문제로 실행하지 못함
* 기존 오류와 이번 변경의 관련성을 확정하지 못함
* 레이어 분류가 애매한 선언이 남아 있음
* 대상 외 기존 변경 때문에 diff 원인을 완전히 분리하기 어려움
* 전체 프로젝트 검사만 실패했고 대상 파일과 관련성을 확인하지 못함

#### `변경 발견`

다음 중 하나라도 해당하면 사용한다.

* 코드 동작에 영향을 줄 수 있는 표현식 변경
* 식별자 또는 공개 인터페이스 변경
* API method, endpoint, parameter, response 처리 변경
* hook 호출 순서 변경
* side effect 실행 순서 변경
* 초기화 시점 변경
* 파일 생성, 삭제 또는 분리
* 함수 본문 리팩터링
* 분류를 위해 코드가 새 함수로 추출되거나 병합됨
* 포맷터가 의미 있는 코드 변경을 발생시킴
* 명확한 레이어 오분류가 다수 존재함

레이어 오분류만 존재하고 코드 동작은 보존된 경우에는 다음과 같이 구분해 보고할 수 있다.

```text
동작 보존: 확인됨
구조 분류: 변경 필요
종합 판정: 주의 필요
```

## 최종 보고 형식

다음 순서로 보고한다.

### 기능 블록

실제로 생성된 기능 블록을 나열한다.

예:

* 공통기능
* 품목 검색 기능
* 그리드 초기화 기능
* 저장 기능
* 화면 설정

각 기능 블록에 포함된 레이어도 함께 작성한다.

예:

```text
- 공통기능: type, hook, helper
- 품목 검색 기능: api, container, helper
- 저장 기능: container
```

### 구조 분류 확인

다음 중 하나로 명시한다.

* `적절함`: 확인한 선언이 레이어 기준에 부합함
* `수정 필요`: 명확한 오분류가 존재함
* `주의 필요`: 일부 선언의 책임이 혼합되어 정적 판단이 어려움

오분류가 있으면 다음 형식으로 작성한다.

```text
- `wr`: lib → helper 권장
  - 근거: `useI18n()`에서 획득한 `t`와 현재 locale에 의존함
- `openDetail`: helper → container 권장
  - 근거: modal 호출이라는 부수 효과를 발생시킴
```

분류 변경을 권장하더라도 검증 단계에서 코드 본문을 수정하지 않는다.

### 동작 보존 확인

다음 중 하나로 명시한다.

* `확인됨`: diff와 검사에서 의미 변경을 발견하지 못함
* `주의 필요`: 정적 검토상 위험 요소가 남아 있음
* `변경 발견`: 주석 및 위치 이동 이외의 의미 변경이 존재함

확인 근거를 함께 작성한다.

예:

```text
동작 보존: 확인됨

근거:
- 기존 import와 export가 유지됨
- 선언 이름과 함수 본문이 보존됨
- API endpoint 및 요청 파라미터 변경 없음
- hook 호출 상대 순서 유지
- 위치 이동된 선언의 초기화 시점 변경 없음
```

### API 및 인터페이스 확인

다음 항목을 간단히 보고한다.

```text
- 식별자: 변경 없음
- import/export: 변경 없음
- API method 및 endpoint: 변경 없음
- 요청 파라미터: 변경 없음
- 응답 처리: 변경 없음
- 이벤트 연결: 변경 없음
```

변경이 있으면 파일과 위치를 명시한다.

### 검사 결과

각 명령과 결과를 개별적으로 작성한다.

```text
- 포맷: `pnpm format:check` — 성공
- lint: `pnpm lint` — 성공
- 타입: `pnpm typecheck` — 성공
```

실패한 경우 핵심 오류와 이번 변경과의 관련성을 구분한다.

예:

```text
- 타입: `pnpm typecheck` — 실패
  - 대상 파일 관련 오류: 없음
  - 기존 오류 추정: `src/legacy/foo.ts`의 unresolved import
  - 이번 변경과의 관련성: 확인되지 않음
```

실행하지 않은 검사는 다음처럼 작성한다.

```text
- 테스트: 미실행 — 프로젝트 지침상 필수 항목이 아님
```

### 변경 파일

수정되거나 생성된 파일을 나열한다.

예:

```text
- 수정: `src/pages/items.vue`
- 생성: 없음
- 삭제: 없음
```

단일 페이지 정리 요청에서는 원칙적으로 대상 파일 하나만 존재해야 한다.

대상 외 파일이 기존 작업 트리에 이미 수정되어 있었다면 별도로 구분한다.

### 이동하지 못한 코드

안전 문제로 원래 위치를 유지한 선언이 있으면 작성한다.

예:

```text
- `watchSelectedRow`
  - 유지 이유: watcher 등록 순서 변경 가능성이 있어 기존 위치를 보존함
```

없으면 `없음`이라고 작성한다.

### 잔여 위험

정적으로 확인할 수 없거나 실행 환경 때문에 검증하지 못한 사항만 작성한다.

예:

```text
- 전체 타입 검사는 generated type 부재로 실행하지 못함
- 이동된 computed와 watcher의 런타임 등록 순서는 정적 검토만 수행함
```

잔여 위험이 없으면 `없음`이라고 작성한다.

### 최종 판정

다음 형식으로 작성한다.

```text
- 구조 분류: 적절함
- 동작 보존: 확인됨
- 포맷 검사: 성공
- 타입 검사: 성공
- 종합 판정: 확인됨
```

구조 분류에 문제가 있지만 동작은 보존된 경우 다음처럼 작성한다.

```text
- 구조 분류: 수정 필요
- 동작 보존: 확인됨
- 포맷 검사: 성공
- 타입 검사: 성공
- 종합 판정: 주의 필요
```
