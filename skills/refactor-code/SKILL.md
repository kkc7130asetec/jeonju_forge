# 동작 보존형 코드 리팩터링

## 목표

사용자가 지정한 범위 안에서 코드의 외부 관찰 가능 동작, 기존 public API, 호출 계약을 유지하면서 책임과 의도를 더 명확하게 만든다. 리팩터링의 품질은 함수 줄 수가 아니라 책임 경계, 응집도, 변경 이유의 명확성으로 판단한다.

## 우선순위

충돌 시 다음 순서를 따른다.

1. 외부 동작 보존
2. 기존 public API와 호출 계약 보존
3. 최소 변경 범위
4. 책임 분리와 응집도 개선
5. 가독성, 중복 제거, 추상화 개선

더 나은 구조를 만들 수 있어도 동작 변경, 계약 변경, 불필요한 추상화 또는 범위 확장을 유발하면 수행하지 않는다.

## 작업 전 확인

먼저 로컬 지침, `AGENTS.md`, 관련 호출부, 테스트, 포맷·타입·빌드 명령을 확인한다. 대상 코드의 입력, 출력, 상태 변경, I/O, 예외 전달, 실행 순서, 초기화 순서를 파악한다. 조회와 상태 변경을 분리할 수 있는지 검토하되, 원자성·트랜잭션·락·일관성 경계가 필요한 경우에는 분리하지 않는다.

## 리팩터링 원칙

- 하나의 함수는 하나의 명확한 책임과 변경 이유를 갖는다. 함수 크기 자체를 줄이는 것을 목표로 삼지 않는다.
- 여러 동작의 순서와 흐름만 조정하는 오케스트레이션 함수는 `Workflow` 접미사를 사용한다. `Workflow` 함수에는 세부 비즈니스 로직을 넣지 않고 책임 있는 함수의 조합과 실행 순서만 둔다.
- 함수 이름만으로 주요 동작과 의도를 추론할 수 있게 한다. 외부 상태 변경이나 I/O는 이름에서 부수효과가 드러나게 한다.
- 복잡한 조건식은 도메인 개념이나 의도를 표현하는 함수로 추출한다.
- 의미 있는 숫자·문자열은 이름 있는 상수, enum, value object 등으로 표현한다. 단, 실제 도메인 의미나 반복 사용이 없으면 추상화하지 않는다.
- 순수 계산과 외부 의존성을 분리하고, 시간·랜덤·DB·네트워크·파일 시스템은 테스트 가능한 경계에 둔다.
- 예외는 복구·변환·표시할 책임이 있는 계층에서 처리한다. 처리할 수 없는 예외를 잡거나 삼키지 않는다.
- 중복 제거보다 도메인 개념과 책임 분리를 우선한다.
- 현재 요구사항이나 실제 변형 지점이 없는 추상화, 범용 유틸리티, 미래 대비 계층은 추가하지 않는다.
- 주석은 코드의 동작 설명이 아니라 제약, 의사결정 배경, 보존해야 하는 이유를 기록할 때만 추가한다.

## 안전한 변경 범위

기존 public API, export, 매개변수와 반환 계약, 오류 의미, 부수효과, 호출 순서, 트랜잭션 경계, hook/lifecycle 규칙을 유지한다. 이름 변경이나 시그니처 변경은 리팩터링에 반드시 필요하고 모든 호출 계약을 안전하게 갱신할 수 있을 때만 한다. 관련 없는 파일과 문제를 함께 정리하지 않는다.

다음은 특히 신중하게 검토한다.

- 함수 추출로 평가 순서, `this`, closure, 초기화 시점이 바뀌는 경우
- 조회와 변경을 분리하면서 원자성이나 트랜잭션 경계가 깨지는 경우
- 비동기 순서, 재시도, 취소, 중복 호출 방지 의미가 바뀌는 경우
- 예외를 새 계층에서 처리해 호출자가 관찰하는 오류가 달라지는 경우
- 상태 저장 위치나 전역 의존성을 바꾸는 경우

## 권장 절차

1. 대상과 변경하지 않을 계약을 먼저 기록한다.
2. 호출 그래프와 상태·I/O 경계를 확인한다.
3. 책임이 섞인 지점을 식별하고, 가장 작은 안전한 변경 단위를 선택한다.
4. 의미가 드러나는 이름과 도메인 경계를 적용한다.
5. 순수 로직, 조회, 상태 변경, 외부 I/O, 오케스트레이션을 필요할 때만 분리한다.
6. `Workflow` 함수는 조합과 순서만 남기고 세부 규칙은 책임 함수에 둔다.
7. 기존 테스트를 실행한다. 테스트가 없으면 변경 전후 핵심 입력·출력·상태·오류·호출 순서를 직접 검증한다.
8. 포맷, 타입 검사, 린트, 관련 테스트를 프로젝트 관례에 맞게 실행한다.
9. 변경 diff를 검토해 범위 밖 수정과 계약 변경이 없는지 확인한다.

## 판단 기준

다음 질문에 답할 수 없는 변경은 보류하거나 더 작은 단위로 되돌린다.

- 무엇이 외부에서 관찰 가능한 동작이며 그대로 보존되었는가?
- 각 함수의 입력, 출력, 상태 변경, I/O 범위가 명확한가?
- 이 함수가 변경되는 이유는 하나인가?
- 이름만 보고 부수효과와 주요 의도를 알 수 있는가?
- 추출·분리로 실행 순서나 원자성이 변하지 않았는가?
- public API와 기존 호출 계약이 유지되는가?
- 검증 결과가 실제 동작 보존을 뒷받침하는가?

## 결과 보고

최종 응답에는 변경한 파일과 핵심 책임 경계, 보존한 계약, 실행한 검증 명령과 결과, 남겨둔 애매한 지점 또는 리스크를 간결하게 기록한다. 테스트 실패나 검증하지 못한 항목은 성공한 것처럼 표현하지 않는다.
